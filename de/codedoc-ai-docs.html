CodeDoc for Confluence — Dokumentation

Zeige Versionen, Konfigurationswerte, README-Abschnitte und Git-Code auf jeder Confluence-Seite und halte sie aktuell. Optional: Lasse KI vollständige Dokumentationsseiten schreiben.

Schnellstart

  1. Installiere CodeDoc aus dem Atlassian Marketplace (30 Tage kostenlos testen) und öffne Apps → CodeDoc.
  2. Verbinde Git mit einem Token nur für Lesezugriff. Mehr brauchen Synchronisierungsblöcke nicht; die Schnellstartanleitung beschreibt die Token-Einrichtung je Anbieter.
  3. Ergänze die für CodeDoc zugänglichen Repositories unter Repositories .
  4. Bearbeite eine Seite, öffne das Makromenü mit / und wähle CodeDoc Sync Block . Füge einen Dateilink ein, prüfe die Vorschau, speichere und veröffentliche.
  5. Optional: Erstelle eine KI-Seite mit Atlassian AI (Advanced-Edition) oder eigenem KI-Schlüssel.

Übersicht

CodeDoc hält Confluence-Seiten auf zwei Arten mit deinem Code synchron:

  • Synchronisierungsblöcke: Ein Synchronisierungsblock übernimmt Fakten aus einer Datei auf die Seite, etwa Helm-Chart-Version, YAML-Einstellungen, README-Abschnitt, neuesten CHANGELOG-Eintrag oder Codeausschnitt. Ohne KI und ohne KI-Schlüssel. Mehr erfahren
  • KI-Seiten (optional): KI schreibt vollständige Dokumentationsseiten aus deinem Code, mit Atlassian AI (Advanced-Edition) oder eigenem Anthropic-, OpenAI- oder Google-Gemini-Schlüssel. Mehr erfahren

Die App liest GitHub, GitLab, Bitbucket Cloud, Azure DevOps und eigene GitHub-Enterprise- oder GitLab-Server, auch über mehrere Verbindungen zugleich. Seiten aktualisieren sich bei jedem Push, täglich oder wöchentlich, mit einer Seitenversion je echter Änderung.

Funktionsweise

  1. Git verbinden mit einem Token nur für Lesezugriff. Ein KI-Schlüssel ist optional und später ergänzbar.
  2. Repositories hinzufügen: Durchsuche dein Git-Konto oder füge eine Repositoryadresse ein.
  3. Synchronisierungsblock hinzufügen: Bearbeite eine Seite, öffne das Makromenü mit / und wähle CodeDoc Sync Block, füge den Dateilink ein und wähle den Inhalt (Synchronisierungsblöcke).

Installation

  1. Suche CodeDoc im Atlassian Marketplace, klicke auf Try it free (Kostenlos testen) (30 Tage Testphase) und wähle deine Confluence-Cloud-Website.
  2. Öffne in Confluence Apps → CodeDoc. Beim ersten Start erscheint der Einrichtungsassistent.

Ersteinrichtung

Der Einrichtungsassistent hat drei Schritte: Git verbinden (erforderlich), KI-Seiten (optional) und Ready (Bereit). Ein CodeDoc-Administrator führt ihn aus; Confluence-Administratoren sind immer Administratoren.

Git verbinden

CodeDoc liest nur Dateien. Deshalb genügt ein Token mit read (Lesen) als Berechtigung. Welche Tokens die Anbieter benötigen: Unterstützte Anbieter.

  1. Wähle den Git-Anbieter: GitHub, GitLab, Bitbucket Cloud, Azure DevOps oder dein eigener Server mit GitHub Enterprise oder GitLab self-managed (Details). Ein Hinweis nennt den benötigten Token samt direktem Link.
  2. Trage ein: Zugriffstoken. Bei Azure DevOps trage zusätzlich die Organisations-URL ein (https://dev.azure.com/your-org).
  3. Optional kannst du einen Anzeigenamen festlegen, etwa „GitHub Arbeit“, und auf Connect and continue (Verbinden und fortfahren) klicken. Funktioniert der Token nicht, nennt die Meldung den Grund.

KI-Seiten (optional)

Mit der Advanced-Edition ist Atlassian AI enthalten: Klicke auf Continue with Atlassian AI (Mit Atlassian AI fortfahren). Andernfalls klicke auf Skip, use sync blocks only (Überspringen, nur Synchronisierungsblöcke verwenden) oder Connect an AI provider (KI-Anbieter verbinden) für einen eigenen Schlüssel. Das lässt sich jederzeit ändern unter Settings → Connections (Einstellungen → Verbindungen).

Eigenen KI-Anbieter verbinden
  1. Wähle Anthropic, OpenAI oder Google Gemini und füge deinen API-Schlüssel ein: Anthropic, OpenAI, Google AI Studio.
  2. Klicke auf Connect (Verbinden). CodeDoc prüft den Schlüssel und lädt die vollständige Modellliste des Anbieters.
  3. CodeDoc wählt ein ausgewogenes, schnelles Modell vor. Wähle bei Bedarf ein anderes in der durchsuchbaren Liste Model (Modell) ; Empfehlungen stehen oben.

Schnelle Modelle (Claude Haiku, GPT-mini-Modelle, Gemini Flash) schreiben eine Seite für mittlere Repositories für wenige Cent. Setze im Anbieterkonto ein Ausgabenlimit.

Repositories

Repositories : Diese Registerkarte listet die für CodeDoc zugänglichen Repositories. Nur diese stehen für Blöcke und KI-Seiten zur Verfügung. Nur CodeDoc-Administratoren dürfen sie hinzufügen oder entfernen.

  • Browse repositories (Repositories durchsuchen): Bei mehreren Git-Verbindungen wähle zuerst die Verbindung. Suche, markiere die Repositories und klicke auf Add N Selected Repository(ies) (N ausgewählte Repositories hinzufügen). Die Liste zeigt bis zu 100 Repositories.
  • Add by address (Per Adresse hinzufügen): Füge die Adresse ein, etwa https://github.com/org/repo; auch Datei- oder Branchlinks funktionieren. Lasse Branch leer für den Standardbranch und klicke auf Add Repository (Repository hinzufügen). CodeDoc prüft zuerst den Zugriff.
GitLab-Untergruppen, Bitbucket und eigener Server

Add by address (Per Adresse hinzufügen) funktioniert mit allen Tokentypen und ist die einzige Möglichkeit bei Bitbucket-Zugriffstokens, die keine Repositories auflisten können. GitLab-Projekte in Untergruppen (group/subgroup/project) werden unterstützt. Bei eigenem GitHub-Enterprise- oder GitLab-Server verbinde ihn zuerst unter Settings → Connections und füge dann hier Repositories hinzu. Bei Fehlern nennt die Meldung Repository und verwendete Verbindung.

Synchronisierungsblöcke

Ein Synchronisierungsblock zeigt und aktualisiert einen Wert, eine Tabelle, einen Abschnitt oder Code aus einer Repositorydatei auf einer Confluence-Seite. CodeDoc kopiert exakt den Dateiinhalt: keine KI-Aufrufe, kein KI-Schlüssel, keine Tokenkosten.

Der synchronisierte Text liegt wie getippter Inhalt auf der Seite; Confluence-Suche, PDF-/Word-Export und Seitenverlauf enthalten ihn. CodeDoc schreibt nur bei Git-Änderungen. Bei nicht lesbaren Dateien behält der Block seinen letzten gültigen Inhalt und erklärt den Fehler.

Synchronisierungsblock hinzufügen

  1. Bearbeite eine Seite, öffne das Makromenü mit / und wähle CodeDoc Sync Block.
  2. Füge den Dateilink ein (aus der Adresszeile bei geöffneter Datei im Git-Anbieter) und klicke auf Use link (Link verwenden). CodeDoc setzt Repository, Branch und Pfad. Das Repository muss auf der Registerkarte Repositories vorhanden sein. Oder wähle das Repository und die Datei unter Find a file (Datei suchen) oder Common files (Häufige Dateien).
  3. Wähle den anzuzeigenden Inhalt (Tabelle unten). Statt Schlüsselpfad, Überschrift oder Ausschnittname einzutippen, klicke auf Show the keys of the file (Dateischlüssel anzeigen) (oder Überschriften oder Ausschnitte) und wähle aus der Liste.
  4. Wähle wie oft CodeDoc den Block aktualisiert.
  5. Klicke auf Show preview (Vorschau anzeigen), dann auf Save (Speichern): Der Inhalt erscheint sofort im Editor. Veröffentliche die Seite; ab dann hält CodeDoc den Block aktuell.

Jedes Feld hat ein (?) mit kurzer Erklärung. Zum späteren Ändern bearbeite die Seite, wähle den Block und klicke auf das Stiftsymbol (Edit).

Schlüsselpfadsyntax, Ausschnittmarkierungen und Überschriften

Schlüsselpfade: Schlüssel mit Punkten trennen (image.tag), Listeneinträge über Index (containers[0].image), alle Einträge mit * (services.*.image.tag) und Schlüssel mit enthaltenen Punkten in Anführungszeichen (labels["app.kubernetes.io/version"]). Ausschnittmarkierungen: Neben codedoc:start / codedoc:end funktionieren auch AsciiDoc-Tags (tag::install[] … end::install[]) und [START install] … [END install] . Ausschnitte erscheinen als Code mit Syntaxhervorhebung, Markdown-Dateien formatiert.

Überschriften eine Ebene kleiner: Für Markdown-Inhalte kannst du Make headings one level smaller (Überschriften eine Ebene kleiner machen) aktivieren. Eine Überschrift mit # wird dann Ebene 2 und passt unter die Seitenüberschriften.

Suchquellen und übertragene Daten

Suchquelle: Automatically (Automatisch) erkennt Imagereferenzen (nginx:1.25.3 oder ein Helm-Wert image.tag neben image.repository), Abhängigkeiten in package.json und name==version in den Zeilen von requirements.txt. Wähle für andere Werte Quelle und Name: Docker-Hub-Image, npm- oder PyPI-Paket, Releases eines GitHub-Projekts (owner/repository) oder Produkt auf endoflife.date.

Images werden mit Tags desselben Formats verglichen: 1.25.3-alpine mit dem neuesten x.y.z-alpine, 20-alpine mit dem neuesten NN-alpine. Vorabversionen werden ausgelassen. Images außerhalb von Docker Hub (ghcr.io, quay.io, private Registrys) werden noch nicht geprüft.

Datenschutz: Nur der öffentliche Image- oder Paketname (etwa nginx oder react) wird an die öffentliche Registry gesendet, nie Datei oder Repository, und nur bei aktivierter Prüfung. Für GitHub-Releases enthält die Anfrage auch deinen verbundenen github.com-Token, der nur das Anfragelimit erhöht. Aktiviere dies nicht für interne Paketnamen. Antworten bleiben 12 Stunden gespeichert; ein Prüfdatum wird nicht angezeigt, damit sich die Seite nur bei geänderter Antwort ändert. Blöcke mit „On every push“ werden bei aktivierter Prüfung auch täglich ausgeführt, da neue Releases ohne Push erscheinen.

Aktualisierungsregeln

HäufigkeitVerhalten
Daily (Täglich) oder Weekly (Wöchentlich)CodeDoc prüft die Datei täglich oder wöchentlich und ändert die Seite nur bei geändertem Inhalt.
On every push to the branch (Bei jedem Push auf den Branch)Der Block aktualisiert sich sofort nach einem Push. Dafür muss der Webhook von CodeDoc im Repository eingerichtet sein (Webhook-Einrichtung); eine Webhook-URL bedient KI-Seiten und Synchronisierungsblöcke.
Only manually (Nur manuell)Der Block ändert sich nur beim Klick auf Update now (Jetzt aktualisieren).

Unabhängig von der Regel darf ein Job Operator auf Update now (Jetzt aktualisieren) am Block oder unter Sync blocks klicken. Ohne Änderungen meldet der Block dies und die Seite bleibt unverändert.

Wer Synchronisierungsblöcke einrichten darf

Nur Nutzer mit der Rolle Job Operator oder Administrator (Rollen) dürfen die Inhaltsquelle eines Blocks wählen. Seitenbearbeiter ohne CodeDoc-Rolle können keine Repositorydateien auf die Seite übernehmen.

So funktioniert die Freigabe
  • Im Blockdialog gespeicherte Einstellungen gelten als freigegeben: Nach Veröffentlichung der Seite beginnt die Synchronisierung beim ersten Aufruf.
  • Anderweitig auf die Seite gelangte Einstellungen (mit Seite oder Vorlage kopiert, per API geschrieben oder später geändert) zeigen Waiting for approval (Warten auf Freigabe) , bis ein Job Operator mit Seitenbearbeitungsrechten Repository, Datei, Branch, Inhalt, Aktualisierungsregel und Versionsprüfung prüft und anschließend Approve and sync (Freigeben und synchronisieren) anklickt.
  • Ein Block liest nur Dateien seines verbundenen Repositories. Pfade und Branches, die ../ enthalten (auch geschrieben als %2e%2e), Rückstrichen oder Steuerzeichen werden abgelehnt (Settings incomplete (Einstellungen unvollständig) mit Erklärung).
  • Zugriffstokens bleiben in CodeDoc. Die auf der Seite gespeicherten Blockeinstellungen enthalten nur Repository, Pfad und Optionen.

Alle Synchronisierungsblöcke verwalten

Synchronisierungsblöcke : Diese Registerkarte listet alle Blöcke mit Seite, Quelle, Inhaltsart, Aktualisierungsregel, Status, letzter Prüfung und gegebenenfalls Abhilfe. Filtere mit Needs attention (Handlungsbedarf), starte einen Block über Update now (Jetzt aktualisieren) oder stoppe die Synchronisierung mit Remove (Entfernen) (der Inhalt bleibt als normaler Text auf der Seite). Remove detached (Nicht mehr verbundene Einträge entfernen) löscht Einträge nicht mehr vorhandener Seiten oder Blöcke.

Gut zu wissen

Grenzen und Verhalten der Synchronisierungsblöcke
  • Dateien bis 1 MB. Ausschnitte, Zeilenbereiche und vollständige Dateien werden bis 20.000 Zeichen angezeigt; Markdown-Abschnitte haben keine Zeichengrenze, nur die 1-MB-Dateigrenze. Bis zu 20 Schlüsselpfade oder 50 Tabellenzeilen pro Block, reguläre Ausdrücke bis 200 Zeichen.
  • Änderungen innerhalb eines Blocks werden bei der nächsten Aktualisierung ersetzt. Schreibe eigenen Text darüber oder darunter.
  • Jede echte Aktualisierung erstellt eine Seitenversion; Confluence benachrichtigt Seitenbeobachter wie bei anderen Änderungen.
  • Relative Markdown-Links führen zur Datei im Git-Anbieter; Bilder erscheinen als Links, da Confluence Bilder privater Repositories nicht laden kann. Die Quellenzeile unter jedem Block verlinkt die Datei.
  • Ohne aktive Lizenz bleiben 3 Synchronisierungsblöcke aktuell; zuvor freigegebene Blöcke laufen weiter (Editionen).

KI-Seiten (optional)

Eine KI-Seite (in früheren Versionen Job genannt) definiert Inhalt, Schreibstil und Veröffentlichungsziel. Sie benötigt Atlassian AI (Advanced-Edition) oder einen verbundenen KI-Anbieter (Settings → Connections (Einstellungen → Verbindungen)).

KI-Seiten : Dieser Bereich hat drei Unterregisterkarten: Pages (Seiten) (Run, Edit, Copy, Delete — Ausführen, Bearbeiten, Kopieren, Löschen), Durchläufe und Schreibstile. New AI page (Neue KI-Seite) öffnet einen Editor mit vier Schritten:

  1. Quelle: Seitenname, bis zu zwei Repositories mit Branch und Ordner sowie die von der KI gelesenen Dateien (Dateiauswahl).
  2. Content (Inhalt): Schreibstil, Sprache und maximale Seitenlänge; optional beginnen mit einem gespeicherten Stil.
  3. Target page (Zielseite): Bereich, übergeordnete Seite und Prüfung jedes Durchlaufs (Prüfung und Rückgängig machen).
  4. Aktualisierungen: manuell, bei jedem Push oder nach Zeitplan, mit Zusammenfassung der CodeDoc-Aktionen.
KI-Seite bearbeiten oder kopieren

Next (Weiter) nennt noch fehlende Angaben eines Schritts. Edit (Bearbeiten) ändert eine bestehende KI-Seite: Go to step (Zum Schritt) springt zum gewünschten Bereich und Save changes (Änderungen speichern) funktioniert aus jedem Schritt (die Seite selbst ändert sich beim nächsten Durchlauf). Copy (Kopieren) erstellt eine neue KI-Seite mit denselben Einstellungen einschließlich Zielbereich.

Ausführungszeitpunkt einer KI-Seite

Schritt 4 legt die Ausführung fest. Alle drei Optionen funktionieren in jeder Edition und ohne aktive Lizenz („On every push“ benötigt das Webhook-Geheimnis).

AktualisierungsregelFunktionsweise
Manually (Manuell)Klicke auf Run (Ausführen) auf der KI-Seite.
On every push (Bei jedem Push)Startet nach einem Push auf den konfigurierten Branch. Benötigt den Webhook (unten).
On a schedule (Nach Zeitplan)Startet täglich, wöchentlich oder monatlich. Alle Zeiten sind UTC.

Webhook-Einrichtung

Webhook-URL bedient alle KI-Seiten und Synchronisierungsblöcke mit „On every push“. Kopiere sie aus Settings → Webhook (Einstellungen → Webhook) und ergänze sie als Webhook in jedem Repository. CodeDoc ordnet Ereignisse über Repositoryadresse und Branch KI-Seiten und Blöcken zu; dieselbe URL funktioniert überall. Jeder Webhook braucht das Webhook-Geheimnis aus Settings → Webhook (Einstellungen → Webhook) (Create secret (Geheimnis erstellen)): Ohne es verarbeitet CodeDoc keine Webhook-Aufrufe.

Push-Ereignisse genügen überall, da auch ein Merge in den Branch ein Push ist. CodeDoc akzeptiert außerdem die unten genannten Merge-Ereignisse; andere Ereignisse (etwa GitHub issues oder Bitbucket repo:fork) werden ignoriert.

GitLabPush-Ereignisse (Push Hook) und Merge-Request-Ereignisse (Merge Request Hook; jedes zählt, auch Öffnen oder Aktualisieren)Push: Branch des Pushs. Merge Request: Zielbranch

  2. Trage ein: Webhook-URL. Falls du ein Webhook-Geheimnis erstellt hast, füge es ein unter Secret token (Geheimnistoken).

Bitbucket: Webhook hinzufügen

  2. Gib einen Titel ein (etwa „CodeDoc“) und trage ein: Webhook-URL. Falls du ein Webhook-Geheimnis erstellt hast, füge es ein unter Secret (Geheimnis).
  3. Wähle unter „Triggers“ Repository → Push (repo:push) und klicke auf Save (Speichern).
Azure DevOps: Service Hook hinzufügen
  1. Project settings (Projekteinstellungen) → Service hooks → Create subscription (Abonnement erstellen) → Web Hooks.
  2. Wähle das auslösende Ereignis Code pushed.
  3. Trage ein: Webhook-URL. Falls du ein Webhook-Geheimnis erstellt hast, wähle Basic authentication (Basisauthentifizierung): beliebiger Nutzername, Geheimnis als Passwort. Klicke auf Finish (Fertigstellen).

Auf eigenen GitHub-Enterprise- oder GitLab-Servern sind die Schritte gleich; der Server muss die Webhook-Adresse im Internet erreichen können.

Geplante Aktualisierungen

Ein Zeitplan schreibt die Seite regelmäßig neu, ohne Webhook. Wähle in Schritt 4 Daily (Täglich) (früheste Stunde, 0–23 UTC), Weekly (Wöchentlich) (Wochentag und Stunde) oder Monthly (Monatlich) (Tag 1–28 und Stunde). Aktiviere Write the page once right after saving (Direkt nach dem Speichern einmal erstellen) für eine sofortige erste Version.

Zeitpunkt: Atlassian prüft Zeitpläne stündlich, deshalb startet ein Durchlauf innerhalb etwa einer Stunde nach der eingestellten Zeit. „Daily 02:00 UTC“ läuft zwischen 02:00 und etwa 03:00 UTC.

Dateiauswahl

In Schritt 1 liest CodeDoc die Dateiliste gewählter Repositories und Ordner und zeigt drei Zahlen: die gefundenen Codedateien, die Anzahl der pro Durchlauf gelesenen Dateien und die geschätzte KI-Eingabe in Tokens im Vergleich zur Grenze unter Settings → AI limits. Bei Atlassian AI erscheint auch der maximale Creditverbrauch pro Durchlauf.

  • Automatically (recommended) (Automatisch, empfohlen): Bis zu 30 Codedateien werden vollständig gelesen. Bei mehr Dateien wählt dein KI-Anbieter pro Durchlauf die wichtigsten bis zur Dateigrenze, einschließlich neuer Dateien; dafür ist ein kleiner zusätzlicher KI-Aufruf nötig.
  • From my file list (Aus meiner Dateiliste): Jeder Durchlauf liest genau deine ausgewählten Dateien. CodeDoc beginnt mit den wichtigsten (Einstiegspunkte, Konfiguration, READMEs); Suggest files with AI (Dateien mit KI vorschlagen) lässt deinen KI-Anbieter eine Liste vorschlagen. Neue Dateien werden nicht automatisch ergänzt.

Um ein Modul eines großen Repositories zu dokumentieren, trage dessen Folder (Ordner) in Schritt 1 ein.

„Too large for one page“ (Zu groß für eine Seite)

Eine Seite wird aus höchstens 50 Dateien (in Settings anpassbar) innerhalb etwa 120.000 Tokens erstellt. Bei mehr als 1.500 Codedateien im gewählten Umfang oder über 10.000 Repositorydateien meldet Schritt 1 „Too large for one page“ (Zu groß für eine Seite) mit Zahlen und nächsten Schritten. Ein trotzdem gestarteter Durchlauf stoppt direkt nach Lesen der Dateiliste vor jedem KI-Aufruf; keine Tokens werden verbraucht. Grenze mit dem Feld Folder (Ordner) ein (ein Modul oder Dienst pro KI-Seite), wähle From my file list (Aus meiner Dateiliste) (dann werden unabhängig von der Repositorygröße nur markierte Dateien gelesen) oder halte einzelne Fakten aktuell mit einem Synchronisierungsblock.

Die Dateiliste wird pro Editorsitzung einmal gelesen; Zurückspringen oder Rückkehr zu einem früheren Ordner fragt Git nicht erneut ab. Dateien anzeigen / Choose files (Dateien auswählen) öffnet die Liste mit Filterfeld; lange Listen zeigen die ersten 60 Dateien und Show all (Alle anzeigen). Nach Ordnerwechsel fallen außerhalb liegende Dateien aus deiner Auswahl.

Dateifilter (erweitert)

Klappe Dateifilter (erweitert) unten im Dateibereich auf, um die Liste mit Glob-Mustern zu verfeinern, eines pro Zeile:

  • Leave out (Auslassen): passende Dateien werden entfernt, zum Beispiel **/*.test.ts, **/__tests__/**, **/migrations/**.
  • Keep anyway (Trotzdem behalten): behält von einem Leave-out-Muster ausgeschlossene Dateien, etwa **/api.test.ts. Es ist keine Positivliste: Passt eine Datei zu keinem Feld, bleibt sie immer enthalten. Für ein einzelnes Verzeichnis verwende das Feld Folder (Ordner) .

**/ benötigt mindestens einen Ordner vor dem Namen. Ergänze deshalb auch *.test.ts , um Testdateien im Repository-Hauptverzeichnis auszuschließen. Bei leeren Feldern gelten die Standards: Buildausgaben, Sperrdateien, minimierte und Binärdateien werden gefiltert; typische Zugangsdaten-Dateien, zum Beispiel .env oder private Schlüssel, werden nie gelesen.

Maximale Seitenlänge

Wähle in Schritt 2 Short (Kurz) (etwa 5–7 Seiten), Standard (etwa 10–15 Seiten, empfohlen) oder Long (Lang) (etwa 20–30 Seiten). Das ist eine Obergrenze, kein Ziel: Die KI stoppt bei vollständigem Inhalt. Bei abruptem Ende wähle länger. Optionen jenseits der Modellkapazität fehlen (etwa Long bei gpt-4o-mini). Administratoren können stattdessen die genaue Anzahl Ausgabetokens aktivieren: Settings → AI limits → Advanced: exact page length in tokens (Erweitert: genaue Seitenlänge in Tokens).

Confluence-Ziel

Jede KI-Seite veröffentlicht in einen Confluence-Bereich, optional unter einer übergeordneten Seite („Root (no parent)“ erstellt auf oberster Ebene). Weitere Durchläufe aktualisieren dieselbe Seite ohne Duplikate.

Titelkonflikte

Confluence-Seitentitel sind pro Bereich eindeutig. Beim Speichern prüft CodeDoc den Bereich; bei Konflikten warnt Schritt 3. Benenne die KI-Seite um oder klicke auf Save anyway (Trotzdem speichern). Die KI-Seite zeigt dann den Hinweis ⚠ Title conflict (Titelkonflikt) und Run (Ausführen) fragt zuerst nach Bestätigung.

Prüfung und Rückgängig machen

Aktiviere Review each run before it is published (Jeden Durchlauf vor Veröffentlichung prüfen) in Schritt 3. Jeder Durchlauf erstellt dann einen Entwurf [DRAFT] <Seitenname> am selben Ort; die KI-Seite zeigt In review (In Prüfung). Die veröffentlichte Seite bleibt bis zur Entwurfsveröffentlichung unverändert. Der Entwurf ist eine normale Seite: Alle mit Bereichszugriff können ihn sehen.

  • Open draft (Entwurf öffnen): Lies oder bearbeite ihn in Confluence.
  • Publish (Veröffentlichen): Die veröffentlichte Seite erhält den Entwurfsinhalt (beim ersten Mal wird der Entwurf selbst zur Seite). Die vorherige Version bleibt im Verlauf.
  • Discard (Verwerfen): Nach Bestätigung landet der Entwurf im Bereichspapierkorb; die veröffentlichte Seite bleibt unverändert.

Letzten Durchlauf rückgängig machen

Hat ein Durchlauf direkt oder über Entwurfsveröffentlichung eine bestehende Seite aktualisiert, bietet die KI-Seite Undo last run (Letzten Durchlauf rückgängig machen). CodeDoc stellt die vorherige Fassung als neue Version wieder her; die KI-Fassung bleibt im Verlauf. Der Durchlauf zeigt Undone (Rückgängig gemacht).

Details zu Prüfung und Rückgängig machen
  • Bei Änderungen nach dem Durchlauf stellt CodeDoc nicht zurück, damit keine Bearbeitungen verloren gehen. Stattdessen nennt es die wiederherstellbare Verlaufsfassung. Bei einer neu erstellten Seite gibt es keine Vorversion; lösche sie in Confluence.
  • Ein verworfener Entwurf lässt sich aus dem Bereichspapierkorb wiederherstellen. Verweigert Confluence die Löschung, nennt die Meldung Grund und Abhilfe; der Entwurf bleibt für einen neuen Versuch verknüpft.
  • Bei erneutem Durchlauf mit wartendem Entwurf landet der alte im Papierkorb und ein neuer wird erstellt. Wartende Entwürfe erscheinen auch unter Needs attention (Handlungsbedarf) in der Übersicht.
  • Ein nach Prüfung veröffentlichter Durchlauf zeigt Published (Veröffentlicht) im Verlauf; ein Klick zeigt veröffentlichende Person und Zeitpunkt.

Gespeicherte Schreibstile

Ein gespeicherter Stil legt Inhaltseinstellungen als benannte Vorlage ab. Erstelle ihn einmal unter AI pages → Writing styles (KI-Seiten → Schreibstile) und starte neue KI-Seiten damit über Start from a saved style (Mit gespeichertem Stil beginnen) in Schritt 2.

Gespeicherte Einstellungen und Änderungsrechte
  • Dokumentationstyp (einer der 8 Stile oder Custom (Eigener Stil) mit eigenen Anweisungen; dein Text ist die vollständige Anweisung), Ausgabesprache, maximale Seitenlänge und Ausschlussmuster.
  • Nur Administratoren dürfen Stile erstellen, bearbeiten, kopieren oder löschen (+ New style (Neuer Stil), Edit (Bearbeiten), Copy (Kopieren), Delete (Löschen)); alle mit Zugriff dürfen sie verwenden.
  • Ein gespeicherter Stil füllt alle passenden Felder zugleich aus; sie bleiben einzeln anpassbar. Direkt in eine KI-Seite eingegebene eigene Anweisungen gelten nur für diese Seite.

Registerkarte Übersicht

CodeDocs erste Ansicht. Bis Repository und Synchronisierungsblock vorhanden sind, zeigt sie die ersten Schritte. Danach:

  • Auf einen Blick: Blöcke und Anzahl mit Handlungsbedarf, letzte Seitenänderung eines Blocks, KI-Seiten und Repositories.
  • Needs attention (Handlungsbedarf): fehlgeschlagene Blöcke, wartende Freigaben, KI-Entwürfe zur Prüfung, fehlgeschlagene KI-Seiten, fast aufgebrauchtes KI-Kontingent und zu ersetzende Bitbucket-Verbindungen, jeweils mit passender Schaltfläche.
  • Letzte KI-Durchläufe: die letzten fünf mit Ergebnis, Modell und Seitenlink.

Durchläufe (KI-Seiten)

AI pages → Runs (KI-Seiten → Durchläufe) protokolliert Zeitpunkt und Wirkung aller Durchläufe. Angezeigt werden die Anzahlen der letzten 30 Tage, Running now (Aktuell laufend) mit Fortschritt und Cancel (Abbrechen) sowie der Run history (Durchlaufverlauf).

Inhalt des Durchlaufverlaufs
  • Jeder Durchlauf, neuester zuerst: Zeit, KI-Seite, Ergebnis (Published (Veröffentlicht), In review (In Prüfung), Discarded (Verworfen), Undone (Rückgängig gemacht), Failed (Fehlgeschlagen)), KI-Anbieter und Modell, gelesene Dateien (etwa „42 of 128“ mit Auswahlmethode), Tokens und Seitenlink. Klicke auf Failed (Fehlgeschlagen) für Grund und Abhilfe.
  • Nächste geplante Durchläufe: Bei geplanten KI-Seiten nächster Durchlauf mit Countdown und letzter Durchlauf.
  • Durchläufe pro Zeitraum: erfolgreiche Durchläufe je Tag, Woche oder Monat.
  • Clear history (Verlauf löschen) (Administratoren) entfernt alle Durchlaufdatensätze; Confluence-Seiten bleiben unverändert.

Einstellungen

Einstellungen : Hier gibt es fünf Registerkarten: Connections (Verbindungen), Webhook, AI limits (KI-Grenzen), Berechtigungen (Administratoren) und Privacy & help (Datenschutz und Hilfe). Nur Administratoren dürfen Einstellungen ändern; Job Operators dürfen sie sehen.

Git-Verbindungen

Verbinde mehrere Anbieter oder Konten gleichzeitig, etwa Arbeits-GitHub, GitLab-Gruppe und eigenen GitLab-Server. Jede Verbindung zeigt Anbieter, Name, Nutzer, Hinzufügungsdatum und Anzahl zugehöriger Repositories; eigene Server tragen die Kennzeichnung Own server (Eigener Server).

Verbindungen hinzufügen und entfernen

Add connection (Verbindung hinzufügen) öffnet dasselbe Formular wie bei der Einrichtung. Remove (Entfernen) löscht den gespeicherten Token und zugehörige Repositories; die letzte Verbindung lässt sich nicht entfernen. Bei Entfernung der letzten Verbindung zu einem eigenen Server entfällt auch dessen Freigabe (Atlassian verlangt eine Bestätigung durch einen Website-Administrator).

KI für KI-Seiten

KI ist optional und nur für KI-Seiten nötig. Die Karte zeigt deine Edition. Mit Advanced (Erweitert) wählst du den Ersteller der Seiten: Atlassian AI (enthalten, ohne Schlüssel; Modell Balanced (Ausgewogen) oder Fast (Schnell) mit Kontingentanzeige) oder deinen eigenen KI-Anbieter (Kontingent).

Für deinen eigenen Anbieter prüft Connect AI provider (KI-Anbieter verbinden) (oder Change provider or key (Anbieter oder Schlüssel ändern)) einen Schlüssel und lädt die Modelle. Turn AI off (KI ausschalten) (Standard) oder Remove own key (Eigenen Schlüssel entfernen) (Advanced) löscht den gespeicherten Schlüssel. Blöcke funktionieren weiter und KI-Seiten bleiben erhalten; mit Advanced laufen sie mit Atlassian AI weiter.

Die Modellliste
  • Model (Modell) : Die Liste enthält alle Textmodelle deines Anbieters, neueste zuerst, mit Recommended (Empfohlen) oben (etwa neueste Sonnet-, Haiku- und Opus-Modelle, GPT und GPT mini, Gemini Pro und Flash). Suche per Eingabe.
  • Refresh list (Liste aktualisieren) lädt seit der Verbindung veröffentlichte Modelle. Audio-, Bild-, Embedding- und andere Nichttextmodelle werden ausgelassen.
  • Bei nicht mehr angebotenem Modell erscheint eine Warnung. Wähle ein anderes, sonst scheitern KI-Seiten mit „model not available“.

Webhook

Zeigt die gemeinsame Webhook-URL für KI-Seiten und Blöcke mit „On every push“, mit kurzen Anleitungen je Git-Anbieter (Webhook-Einrichtung). Ohne Webhook verwende tägliche oder wöchentliche Aktualisierung.

Webhook-Geheimnis (Administratoren): Create secret (Geheimnis erstellen) erstellt ein zufälliges Geheimnis. Es ist erforderlich: CodeDoc nimmt Aufrufe nur mit Geheimnis an, damit niemand sonst über die Adresse Aktualisierungen oder KI-Durchläufe mit deinem KI-Budget auslöst. Ergänze es bei jedem Webhook an CodeDoc. Ohne Geheimnis zeigt die Karte Secret missing (Geheimnis fehlt) und CodeDoc lehnt alle Webhook-Aufrufe ab. „On every push“ lässt sich erst mit vorhandenem Geheimnis speichern.

Weitere Informationen zum Geheimnis

Show secret (Geheimnis anzeigen) und Replace secret (Geheimnis ersetzen) stehen daneben; Entfernen ist nicht möglich. Nach Ersatz aktualisiere es in allen Git-Webhooks. URL und Geheimnis sind für alle Anbieter gleich: GitHub und GitHub Enterprise verwenden das Webhook-Feld Secret (Geheimnis), GitLab Secret token (Geheimnistoken), Bitbucket Secret (Geheimnis), Azure DevOps Basic authentication (Basisauthentifizierung) mit dem Geheimnis als Passwort. Ein Push bei noch wartender KI-Seite startet keinen zweiten Durchlauf; der wartende liest ohnehin den neuesten Commit.

AI limits (KI-Grenzen)

  • Maximale Dateien pro KI-Seite: Standard 50 (Bereich 5–200). Größere Ordner werden auf die wichtigsten Dateien eingegrenzt.
  • Budget für Eingabetokens: gesamter Code pro KI-Durchlauf, Standard 120.000 (Bereich 30.000–500.000). Bleibe unter dem Kontextfenster deines Modells.

Zu große Repositories (mehr als 1.500 Codedateien oder insgesamt 10.000 Dateien) stoppen vor KI-Aufrufen mit Hinweisen zu nächsten Schritten. Blöcke sind von diesen Grenzen nicht betroffen.

Netzwerk und Freigabedetails

CodeDoc läuft in Atlassians Cloud, nicht in deinem Netzwerk. Der Server muss über HTTPS aus dem Internet erreichbar sein, mit Zertifikat einer öffentlichen Zertifizierungsstelle. Bei Firewall erlaube Atlassians ausgehende IP-Adressen (IP-Adressen und Domains für Atlassian-Cloud-Produkte).

Die Freigabe steht unter Atlassian Administration → Connected apps → CodeDoc → Data management („Data storage, sharing, receiving and processing“), wo Administratoren sie entfernen können. Repositories, Dateilinks, Blöcke, KI-Seiten und Webhooks funktionieren danach wie bei Cloud-Diensten.

Bitbucket-Tokens

CodeDoc liest Bitbucket Cloud mit einem Zugriffstoken: Ein Repository-Zugriffstoken (Repository settings → Access tokens, „Repositories: Read“, alle Tarife) oder mit Bitbucket Premium einem Projekt- oder Workspace-Zugriffstoken für mehrere Repositories. Bei Repository-Tokens füge je Repository eine Verbindung hinzu.

Warum persönliche API-Tokens und App-Passwörter nicht akzeptiert werden

Atlassians Sicherheitsanforderungen für Marketplace-Apps verbieten das Sammeln und Speichern von Atlassian-Kontozugangsdaten; Bitbucket-API-Tokens gehören einem Atlassian-Konto. Zugriffstokens gehören dagegen Repository, Projekt oder Workspace. Vor CodeDoc 8 mit persönlichem Token erstellte Verbindungen laufen zunächst weiter und sind zum Ersatz markiert. Ergänze eine Zugriffstoken-Verbindung und entferne die alte.

Datenverarbeitung und Datenschutz

Alle Verarbeitung läuft auf Atlassians Forge-Infrastruktur; es gibt keinen CodeDoc-Server.

  • Synchronisierungsblöcke: Die Forge-Laufzeit liest die gewählte Datei mit deinem Token beim Git-Anbieter und CodeDoc schreibt den ausgewählten Teil in den Block. Nichts geht an KI-Anbieter. CodeDoc speichert Blockeinstellungen und Inhaltsprüfsumme, nicht die Datei.
  • Versionsprüfung (optional): Nur bei aktivierter Prüfung wird der öffentliche Image- oder Paketname (etwa nginx) an die öffentliche Registry gesendet: Docker Hub, npm, PyPI, GitHub-Releases oder endoflife.date. Antworten liegen 12 Stunden im App-Speicher deiner Website. Weder Dateiinhalt noch Repository werden gesendet; GitHub-Releases-Anfragen enthalten den verbundenen github.com-Token.
  • KI-Seiten (optional): Die Forge-Laufzeit lädt gewählte Dateien mit deinem Token; typische Zugangsdaten-Dateien wie .env oder private Schlüssel werden nie geladen. Bei eigenem KI-Anbieter werden Dateien mit deinem API-Schlüssel unter deinem Konto und dessen Datenbedingungen gesendet. Bei Atlassian AI (Advanced) gehen sie an Claude-Modelle auf Atlassians Plattform, ohne externes KI-Konto oder Schlüssel. CodeDoc speichert Dateinamen, Tokenanzahlen und Atlassian-AI-Credits je Durchlauf, nicht den Code.
Eigener KI-Anbieter: Bei eigenen Anbietern geht Quellcode auch an sie und unterliegt deren Verarbeitungs- und Aufbewahrungsregeln. Prüfe die Bedingungen vor Übertragung sensiblen Codes. Bei Atlassian AI bleibt Code auf Atlassians Plattform.
Speicherung, Verschlüsselung, Seitenänderungen und Nutzungsstatistik
  • Alle Übertragungen sind verschlüsselt mit TLS.
  • CodeDoc ruft nur deine Git-Anbieter (einschließlich freigegebener eigener Server), für KI-Seiten deinen KI-Anbieter oder Atlassian AI und bei Versionsprüfung die oben genannten öffentlichen Registrys auf.
  • API-Schlüssel und Zugriffstokens liegen im verschlüsselten Forge-Speicher deiner Confluence-Website. Sie werden nie erneut angezeigt, auf Seiten geschrieben oder protokolliert.
  • CodeDoc erstellt und aktualisiert Seiten als CodeDoc-App: KI-Seiten in gewählten Bereichen, Blöcke nur innerhalb ihres Blocks. Seitenbeschränkungen gegen die App stoppen diese Aktualisierungen.
  • Nutzungsstatistik: CodeDoc zählt Funktionsaufrufe (etwa „Synchronisierungsblock aktualisiert“) websiteübergreifend und schreibt technische Logs, die Atlassian App-Anbietern bereitstellt. Die Zähler enthalten keine Seiten-, Bereichs-, Repository-, Datei- oder Nutzerinformationen.

Fehlerbehebung

Die meisten CodeDoc-Meldungen nennen Ursache und Abhilfe. Hilft das nicht, schreibe an support@janekbehrens.de.

Synchronisierungsblöcke

„the file or the branch does not exist (HTTP 404)“ (Datei oder Branch existiert nicht)

Prüfe den Dateipfad und den Branch in den Blockeinstellungen: Pfade beachten Groß- und Kleinschreibung und beginnen unterhalb des Repository-Hauptverzeichnisses. Kopiere den Pfad beim Git-Anbieter (Teil nach dem Branchnamen). Aktualisiere ihn nach Umbenennung oder Verschiebung. Show preview (Vorschau anzeigen) prüft den Pfad vor dem Speichern.

„Key path … was not found in the file“ (Schlüsselpfad nicht gefunden)

Die Meldung nennt vorhandene Schlüssel an dieser Stelle, beispielsweise Keys under „image“: repository, pullPolicy, tag. (Schlüssel unter „image“) Schlüsselpfade beachten Groß- und Kleinschreibung und funktionieren nur mit YAML und JSON. Für andere Dateien wähle regulären Ausdruck, Zeilenbereich oder vollständige Datei.

„Settings incomplete“ oder „Waiting for approval“ (Einstellungen unvollständig oder Freigabe ausstehend)

Settings incomplete (Einstellungen unvollständig) listet fehlende Einstellungen auf: Bearbeite die Seite, wähle den Block und klicke auf das Stiftsymbol. Waiting for approval (Warten auf Freigabe) bedeutet, dass neue oder geänderte Einstellungen noch nicht freigegeben sind. Ein Job Operator oder Administrator mit Seitenbearbeitungsrechten muss den Block einmal öffnen (Details).

„the Git provider rejected the access token (HTTP 401)“ (Git-Anbieter lehnt Zugriffstoken ab)

Der gespeicherte Token ist ungültig oder abgelaufen. Ein Administrator ersetzt ihn unter Settings → Connections (Einstellungen → Verbindungen). Bis zur nächsten erfolgreichen Aktualisierung bleibt der letzte gültige Blockinhalt erhalten.

„the GitHub organization accepts requests only from addresses on its IP allow list (HTTP 403)“ (GitHub-Organisation akzeptiert nur Adressen ihrer IP-Allowlist)

Deine GitHub-Organisation akzeptiert nur Anfragen von Adressen auf ihrer IP-Allowlist, und CodeDoc liest deine Repositories aus Atlassians Cloud. Ein Owner der Organisation trägt Atlassians ausgehende IP-Bereiche (IPv4 und IPv6) unter Settings → Authentication security → IP allow list ein; in CodeDoc ändert sich nichts. Die Bereiche gelten für Atlassians gesamte Cloud, und GitHub verlangt für jede Anfrage weiterhin dein Zugriffstoken.

„On every push“ aktualisiert nicht

Push-Aktualisierungen benötigen den CodeDoc-Webhook mit Geheimnis im Repository (Webhook-Einrichtung) und einen Push auf den Branch des Blocks (Einstellung Branch oder Standardbranch des Repositories). Update now (Jetzt aktualisieren) prüft den Block zwischenzeitlich.

KI-Seiten

„A Confluence page with this title already exists“ (Seitentitel bereits vorhanden)

Seitentitel sind je Bereich eindeutig. Benenne die KI-Seite um oder benenne beziehungsweise verschiebe die andere Confluence-Seite. CodeDoc warnt beim Speichern vor Konflikten (Confluence-Ziel).

„AI returned empty response“ (Leere KI-Antwort)
  • Eingabetokenbudget zu niedrig: Erhöhe es unter Settings → AI limits.
  • Seitenlänge zu kurz: Erhöhe die Einstellung Maximale Seitenlänge in Schritt 2.
  • Modellgrenzen: Teste ein leistungsfähigeres Modell (etwa Haiku → Sonnet oder GPT mini → vollständiges GPT-Modell).
XHTML-Verarbeitungsfehler

KI-Ausgaben sind manchmal kein gültiges Confluence-Markup. CodeDoc repariert Tags und Makros automatisch; schlägt das fehl, nutzt es ein vereinfachtes Format (Klartext mit Überschriften), sodass die Seite immer entsteht. Starte die KI-Seite erneut.

„Rate limit exceeded“ (429) (Anfragelimit überschritten)

Dein KI-Anbieter begrenzt Anfragen. CodeDoc versucht es bis zu 3-mal mit steigenden Wartezeiten (3, 8, 15 Sekunden). Bei anhaltendem Fehler warte einige Minuten, prüfe Tarifgrenzen und reduziere die gelesene Dateianzahl.

„Insufficient credits/balance“ oder Kontingentmeldung des Anbieters

Dein KI-Konto hat kein Guthaben. Lade es auf bei Anthropic oder OpenAI; prüfe bei Gemini das Kontingent in AI Studio.

Der Anbieter meldet eine zu große Anfrage

Der Code überschreitet die maximale Modelleingabe. Lasse CodeDoc Dateien automatisch wählen oder markiere weniger, reduziere das Eingabetokenbudget, ergänze Muster unter Leave out (Auslassen) oder setze einen Folder (Ordner) (Dateiauswahl) oder wechsle zu einem Modell mit größerem Kontextfenster.

Atlassian AI: „the included AI allowance for this month is used up“ (Monatliches Kontingent aufgebraucht)

Der Durchlauf startete nicht und verbrauchte nichts. Das Kontingent erneuert sich am ersten Tag des nächsten Monats (UTC). Wähle bis dahin Your own AI provider (Eigener KI-Anbieter) unter Settings → Connections oder warte. Bei kleinem Rest können weniger Dateien oder kürzere Seiten noch passen.

Atlassian AI: „declined this request in its content safety check“ (Anfrage bei Inhaltsprüfung abgelehnt)

Atlassian prüft jede Anfrage wie bei eigenen KI-Funktionen. Lasse ungewöhnliche Inhalte aus (AI page → Source → file filters) oder verwende für diese Seite einen eigenen Anbieter.

Eine geplante KI-Seite lief nicht zum erwarteten Zeitpunkt

Zeitpläne werden stündlich geprüft; Durchläufe starten bis etwa eine Stunde nach der eingestellten Zeit. Prüfe nach 2 Stunden ohne Durchlauf die Aktualisierungsregel On a schedule (Nach Zeitplan), den korrekten Eintrag Nächste geplante Durchläufe unter AI pages → Runs und die Gültigkeit von Git-Token sowie gegebenenfalls eigenem KI-Schlüssel.

Die Seite ist zu kurz oder ungenau

Erhöhe die Einstellung Maximale Seitenlänge, ergänze wichtigere Dateien (die KI kann nur erhaltenen Code dokumentieren, also Konfiguration, README und package.json) oder teste ein leistungsfähigeres Modell. KI-Seiten können Fehler enthalten; prüfe sie vor dem Teilen und erwäge Review each run before it is published (Jeden Durchlauf vor Veröffentlichung prüfen).

Webhooks, Verbindungen und Server

Webhook: „Event is not supported“ (Ereignis nicht unterstützt)

Der Webhook sendet ein ungenutztes Ereignis. Sende Push- oder unterstützte Merge-Ereignisse aus der Ereignistabelle; fork, issue, comment und andere werden ignoriert.

Webhook kommt an, aber nichts aktualisiert sich

Keine KI-Seite oder kein Block passt. Prüfe, ob das Repository auf der Registerkarte Repositories mit derselben Adresse wie im Webhook steht, ob der Push auf den konfigurierten Branch erfolgt und ob die Aktualisierungsregel lautet: On every push (Bei jedem Push).

Bitbucket: „personal API tokens and app passwords cannot be used“ (Persönliche API-Tokens und App-Passwörter nicht verwendbar)

CodeDoc akzeptiert nur Bitbucket-Zugriffstokens (Bitbucket-Tokens). Erstelle einen Repository-Zugriffstoken mit „Repositories: Read“ und füge nur den Tokenwert ein.

Bitbucket: „Browse“ zeigt meine Repositories nicht

Bitbucket erlaubt Zugriffstokens keine Repositoryauflistung (die kontoweite Liste wurde 2026 entfernt). Ergänze jedes Repository über Add by address (Per Adresse hinzufügen); dort prüft CodeDoc den Lesezugriff. Mit Bitbucket Premium deckt ein Projekt- oder Workspace-Token mehrere Repositories ab.

Eigener Server: „CodeDoc may not connect to … yet“ oder „could not reach …“ (Verbindung noch nicht erlaubt oder Server nicht erreichbar)
  • Verbindung noch nicht erlaubt: Klicke auf Allow access to the server (Serverzugriff erlauben); ein Website-Administrator bestätigt Atlassians Dialog. Warte direkt nach Freigabe eine Minute und klicke erneut auf Connect (Verbinden) .
  • Nicht erreichbar: Atlassians Cloud kann die Adresse nicht öffnen. Prüfe HTTPS mit öffentlichem Zertifikat und Firewallfreigabe für Atlassians ausgehende IP-Adressen.
  • Erreichbar, aber Token abgelehnt: Token falsch, abgelaufen oder ohne Leseberechtigung (GitHub: Contents read; GitLab: read_api und read_repository).

Häufige Fragen

Verwenden Synchronisierungsblöcke KI oder kosten sie Tokens?

Nein. Ein Synchronisierungsblock kopiert exakt den Dateiinhalt: keine KI-Aufrufe, keine Tokenkosten, keine Übertragung an KI-Anbieter.

Findet die Confluence-Suche den Inhalt eines Synchronisierungsblocks?

Ja. Der synchronisierte Inhalt wird wie normaler Text auf der Seite gespeichert und ist in Confluence-Suche, PDF-/Word-Export und Seitenverlauf enthalten.

Überfüllen Synchronisierungsblöcke den Seitenverlauf?

Nein. CodeDoc schreibt nur bei geändertem Git-Inhalt auf die Seite; jede Seitenversion entspricht einer echten Dateiänderung.

Verbraucht CodeDoc unsere Rovo- oder Atlassian-AI-Kontingente?

Nein. Atlassian AI in CodeDoc Advanced hat ein eigenes monatliches Kontingent im Abonnement. Deine Rovo- und Atlassian-AI-Kontingente bleiben unberührt.

Kann CodeDoc GitLab oder GitHub Enterprise hinter einer Firewall lesen?

Nur bei Erreichbarkeit aus Atlassians Cloud: CodeDoc läuft auf Forge, nicht in deinem Netzwerk. Erlaube Atlassians ausgehende IP-Adressen oder mache den Server über HTTPS erreichbar. Siehe Dein eigener Git-Server.

Was kostet die KI-Nutzung?

Mit Atlassian AI (Advanced) sind KI-Seiten bis zum monatlichen Kontingent ohne Zusatzkosten enthalten. Mit eigenem Schlüssel erhebt CodeDoc keine Gebühr pro Seite; dein KI-Anbieter berechnet Tokens, und der Verlauf zeigt deren Anzahl je Durchlauf. Ein mittleres Repository benötigt typischerweise 10.000–50.000 Eingabe- und 2.000–8.000 Ausgabetokens. Grobe Kosten pro Seite mit eigenem Schlüssel: Google Geminis kostenloser Tarif kostet nichts (Google kann dessen Daten zur Produktverbesserung nutzen); Claude Haiku oder ein GPT-mini-Modell meist 0,01–0,05 USD; größere Modelle (Claude Sonnet, vollständige GPT-Modelle) 0,10–0,50 USD, je nach Repositorygröße.

Kann ich verschiedene KI-Modelle für unterschiedliche KI-Seiten verwenden?

Noch nicht: Alle KI-Seiten verwenden ein Modell. Ändere es jederzeit unter Settings → Connections; der nächste Durchlauf nutzt es.

Kann ich mehrere Repositories auf einer KI-Seite dokumentieren?

Ja, bis zu 2 Repositories pro KI-Seite. Die KI erhält den Code beider und erstellt eine gemeinsame Seite.

Welche Programmiersprachen und Dateitypen werden unterstützt?

Alle Textdateien; es gibt keine Sprachbeschränkung. Wie gut die KI einen Dateityp versteht, hängt vom Modell ab. CodeDoc lässt Abhängigkeiten, Buildausgaben, Sperrdateien, minimierte Dateien, Binär- und Mediendateien aus und liest nie typische Zugangsdaten-Dateien (.env, private Schlüssel, Zertifikate, Terraform-Zustands- und Variablendateien, Zugangsdaten-Dateien), auch nicht bei passenden Einschlussmustern.

In welchen Sprachen kann die Dokumentation erstellt werden?

Englisch, Deutsch, Französisch, Spanisch, Italienisch, Portugiesisch, Japanisch, Chinesisch und Koreanisch stehen in der Liste; Other language… (Andere Sprache) akzeptiert jede eingegebene Sprache (Qualität modellabhängig).

Wo wird meine Dokumentation gespeichert?

Als normale Confluence-Seite im gewählten Bereich. Du kannst sie bearbeiten, verschieben oder löschen. Weitere KI-Durchläufe aktualisieren dieselbe Seite ohne Duplikat. Bei aktivierter Prüfung wird jeder Durchlauf zuerst als [DRAFT] gekennzeichnete Seite gespeichert.

Kann ich Dokumentation vor der Veröffentlichung prüfen?

Ja. Aktiviere Review each run before it is published (Jeden Durchlauf vor Veröffentlichung prüfen) in Schritt 3. Die veröffentlichte Seite ändert sich erst beim Veröffentlichen des Entwurfs in CodeDoc. Discard (Verwerfen) lässt die veröffentlichte Seite unverändert; Undo last run (Letzten Durchlauf rückgängig machen) stellt die Version vor dem Durchlauf wieder her. Siehe Prüfung und Rückgängig machen.

Schreiben Webhook- und Zeitplanaktualisierungen die KI-Seite komplett neu?

Ja. Jede Aktualisierung liest den aktuellen Git-Code, die KI schreibt die Seite neu und CodeDoc aktualisiert die vorhandene Confluence-Seite.

Kann ich private Repositories verwenden?

Ja. CodeDoc verwendet deinen Zugriffstoken. Mit Lesezugriff funktioniert es bei öffentlichen und privaten Repositories.

Wie deinstalliere ich die App?

Gehe zu Confluence Settings → Apps → Manage apps, suche CodeDoc und klicke auf Uninstall (Deinstallieren). Danach kann die App ihre Konfiguration und gespeicherten Daten nicht mehr lesen; Atlassian hält sie 28 Tage vor und löscht sie dann (innerhalb von 21 Tagen kannst du uns um Wiederherstellung in einer neuen Installation bitten). Erstellte Confluence-Seiten bleiben in deinen Bereichen; lösche sie bei Bedarf manuell.
