Von GitHub Wiki zu Confluence: Zwei Migrationswege im Vergleich

Die meisten Entwicklungsteams mit GitHub Wikis stoßen irgendwann an Grenzen — schwache Suche, grobe Berechtigungen und ein Unternehmen, dessen übrige Teams bereits Confluence nutzen. Die naheliegende Frage lautet: „Wie übertragen wir das?“ Die ehrliche Antwort: Wahrscheinlich solltest du nicht alles übertragen. Hier findest du die zwei praktikablen Wege und ihre jeweiligen Einsatzfälle.

Warum Teams GitHub Wiki verlassen

GitHub Wikis sind einfach einzurichten und überraschend schwer zu skalieren. Die häufigsten Gründe für einen Wechsel:

  • Eingeschränkte Suche — die Wiki-Suche deckt nur Titel und einen kleinen Teil des Seitentexts ab. Eine repositoryübergreifende Suche über mehrere Wikis fehlt.
  • Grobe Berechtigungen — wer das Repository lesen kann, kann auch das Wiki lesen. Du kannst der Finanz- oder Rechtsabteilung keine einzelne Seite freigeben, ohne die Codebasis zugänglich zu machen.
  • Außerhalb der Entwicklung schwer auffindbar — Menschen außerhalb der Entwicklung öffnen selten github.com/org/repo/wiki.
  • Der Rest des Unternehmens sucht an einem anderen Ort — wenn jedes andere Team in Confluence schreibt, führen zwei Dokumentationsorte dazu, dass Leser keinen davon prüfen.

Zwei praktikable Wege

Im Wesentlichen gibt es zwei Wege für den Wechsel, die unterschiedliche Fragen beantworten:

Weg A: Inhalte migrieren Weg B: Aus dem Quellcode neu erzeugen
Was übertragen wird Bestehende Wiki-Seiten, genau wie geschrieben Nichts. Frische Dokumentation aus dem aktuellen Code
Bleibt die Historie erhalten? Ja — Formulierungen, Entscheidungen, Screenshots Nein — nur, was heute noch im Code steckt
Werden veraltete Seiten übernommen? Ja, sofern du vorher nicht aussortierst Nein — die KI sieht nur den aktuellen Quellcode
Aufwand Skript mit pandoc + REST-API oder kostenpflichtiges Migrationswerkzeug App einmal verbinden, je Repository erzeugen
Bleibt es aktuell? Nein. Dasselbe Aktualitätsproblem wie zuvor Ja — bei Commit oder nach Zeitplan erneut ausführen
Am besten geeignet für Architekturentscheidungen, RFCs, Nachanalysen API-Referenzen, Modulübersichten, Einarbeitung

Die ehrliche Empfehlung: Nutze beide. Migriere die kleine Teilmenge der Seiten, die Entscheidungen und Historie festhalten (Weg A). Erzeuge die größere Menge an Seiten zu „Was macht dieser Code?“ aus dem Quellcode neu (Weg B). Migriere nicht pauschal alles.

Weg A — Wiki-Inhalte mit pandoc migrieren

Jedes GitHub Wiki ist selbst ein Git-Repository. Du kannst es klonen, Markdown mit dem folgenden Werkzeug in das Confluence-Speicherformat konvertieren: pandoc und das Ergebnis anschließend per REST an Confluence senden.

Schritt 1: Das Wiki-Repository klonen

git clone https://github.com/your-org/your-repo.wiki.git
cd your-repo.wiki
ls *.md

Schritt 2: Markdown in das Confluence-Speicherformat konvertieren

for f in *.md; do
  pandoc "$f" -f gfm -t html -o "out/${f%.md}.html"
done

Pandoc erzeugt XHTML, das für die meisten Seiten nahe genug am Confluence-Speicherformat liegt. Codeblöcke, Überschriften, Listen, Tabellen und Textformatierung werden sauber übernommen. Manuell prüfen musst du relative Seitenlinks, eingebettete Bilder und besondere GitHub-Makros (zum Beispiel <details> -Blöcke).

Schritt 3: Seiten über die Confluence-REST-API erstellen

POST /wiki/rest/api/content
{
  "type": "page",
  "title": "Architecture Overview",
  "space": { "key": "ENG" },
  "body": {
    "storage": {
      "value": "<html content from pandoc>",
      "representation": "storage"
    }
  }
}

Baue die Schleife in ein Skript ein, das jede Markdown-Datei einem Seitentitel und einer übergeordneten Seite zuordnet. Führe es zunächst in einem Testbereich aus, prüfe das Ergebnis und korrigiere das Skript, bevor du es auf den eigentlichen Bereich anwendest.

Achte auf: Interne Wiki-Links in der Form [[Page Name]]. Pandoc erkennt nicht, dass sie auf andere Wiki-Seiten verweisen, und übernimmt sie als einfachen Text. Ersetze sie in einem Nachbearbeitungsschritt durch Confluence-Links mit den neuen Seiten-IDs.

Weg B — Aus dem Quellcode mit CodeDoc AI neu erzeugen

Der zweite Weg überspringt die Migration vollständig. Statt das bestehende Wiki zu übertragen, verbindest du ein KI-Dokumentationswerkzeug mit dem Quellcode-Repository, wählst die Ausgabestruktur und lässt es frische Seiten direkt in Confluence schreiben.

CodeDoc AI for Confluence ist ein solches Werkzeug auf Basis von Atlassian Forge. Der Ablauf:

  1. Einen KI-Anbieter verbinden — nutze deinen eigenen Schlüssel für Anthropic Claude, OpenAI oder Google Gemini.
  2. GitHub verbinden mit einem persönlichen Zugriffstoken (Lesezugriff auf die zu dokumentierenden Repositories).
  3. Das Repository hinzufügen — durchsuchen und auswählen oder die URL mit einem Branch einfügen.
  4. Einen Auftrag erstellen — wähle eine Dokumentationsvoreinstellung (Developer Documentation für Entwicklerdokumentation, Onboarding Guide für Einarbeitung, Quick Reference als Kurzreferenz, Compliance & Audit usw.), eine Sprache und einen Auslöser.
  5. Einen Zielbereich auswählen — wähle den Confluence-Bereich, in dem die Seite erstellt werden soll.
  6. Ausführen — die KI liest den Code, erzeugt strukturierte Dokumentation und veröffentlicht sie als Confluence-Seite.

Was dieser Weg leistet — und was nicht

Das ist kein Migrator für Wiki-Inhalte. CodeDoc AI liest nicht deine GitHub-Wiki-Seiten, sondern den Quellcode im Hauptrepository. Die Ausgabe ist Dokumentation, die den heutigen Stand des Codes abbildet. Wenn dein Wiki ein Architekturentscheidungsprotokoll oder eine Einarbeitungsanleitung enthält, die nicht im Code steckt, musst du diese Inhalte separat übernehmen (dafür eignet sich Weg A).

Dafür bleibt die erzeugte Dokumentation ohne zusätzlichen Aufwand aktuell. Setze den Auslöser auf bei Commit per Webhook oder nach Zeitplan (täglich / wöchentlich / monatlich). Die Confluence-Seiten aktualisieren sich dann bei Codeänderungen automatisch. Das ursprüngliche Problem des Wikis — Seiten, die sich über Jahre vom Code entfernten — wird gelöst, indem die Abhängigkeit von manuellen Aktualisierungen vollständig entfällt.

Tipp: Wenn du es nur ausprobieren möchtest, benötigt die Voreinstellung „Quick Reference“ die wenigsten Tokens — fünf Abschnitte, eine Technologietabelle, wichtige Befehle und die Projektstruktur. Ein mittelgroßes Repository kostet mit Geminis kostenlosem Kontingent typischerweise nur wenige Cent.

Migriere keine ungenutzten Seiten

Der größte Fehler bei einer Wiki-Migration ist, sie als bloßen Kopiervorgang zu behandeln. Die meisten GitHub Wikis enthalten viele unvollständige Entwürfe, alte Architekturskizzen und nicht mehr gültige Anleitungen. Sie nach Confluence zu migrieren bewahrt die Altlasten — und nun sehen sie auch Stakeholder, die zuvor keinen Wiki-Zugriff hatten.

Vor beiden Wegen:

  • Liste jede Wiki-Seite — ls *.md im Wiki-Repository auf und übertrage die Liste in eine Tabelle.
  • Kennzeichne jede Seite mit behalten, neu erzeugen oder archivieren.
  • Behalte die tatsächlich unersetzbaren Seiten — Entscheidungsprotokolle, Nachanalysen und Betriebsanleitungen, die auf menschlichem Wissen statt auf Code beruhen.
  • Erzeuge die Seiten zu „Was macht dieser Code?“ aus dem Quellcode neu.
  • Archiviere den Rest. Wenn eine Seite seit zwölf Monaten niemand angefasst hat, ist sie mit hoher Wahrscheinlichkeit keine tragende Grundlage.

Ein kombinierter Ablauf

Für die meisten Teams ist diese Reihenfolge am sinnvollsten:

  1. Prüfe das Wiki. Kennzeichne Seiten mit behalten / neu erzeugen / archivieren.
  2. Migriere die mit behalten markierten Seiten mit pandoc + REST-API in einen neuen Confluence-Bereich.
  3. Installiere CodeDoc AI, wähle denselben Confluence-Bereich und richte Aufträge für jedes Repository ein.
  4. Verbinde die Aufträge mit deiner CI: Webhook-Auslösung bei einem Push auf main, damit die Dokumentation mit dem Code aktualisiert wird.
  5. Archiviere das alte GitHub Wiki — halte es als schreibgeschützte Referenz vor und verweise in der README auf Confluence.

Häufig gestellte Fragen

Wie migriere ich ein GitHub Wiki nach Confluence?

Zwei praktikable Wege. Der erste ist eine Inhaltsmigration: Klone das Wiki-Repository, konvertiere Markdown mit einem Werkzeug wie pandoc in das Confluence-Speicherformat und importiere das Ergebnis über die Confluence-REST-API. Der zweite ist eine Neuerzeugung: Der Quellcode bleibt in GitHub, aber ein KI-Dokumentationswerkzeug wie CodeDoc AI erstellt daraus frische Dokumentation direkt in Confluence. Der erste Weg erhält die Historie; der zweite vermeidet die Migration veralteter Seiten.

Bietet Atlassian ein Werkzeug zum Import eines GitHub Wikis in Confluence?

Confluence bietet einen Markdown-Import für einzelne Seiten, aber keinen integrierten Migrator für ein vollständiges GitHub-Wiki-Repository. Du importierst entweder Seiten einzeln, automatisierst die Konvertierung mit pandoc und der Confluence-REST-API oder erzeugst die Dokumentation mit einer Marketplace-App aus dem Quellcode neu.

Sollte ich mein gesamtes GitHub Wiki nach Confluence migrieren?

Normalerweise nicht. Die meisten GitHub Wikis enthalten viele veraltete Seiten — unvollständige Entwürfe, alte Architekturskizzen und nicht mehr gültige Anleitungen. Alles zu migrieren übernimmt die Altlasten. Besser ist es, noch aktiv genutzte Seiten zu identifizieren und zu migrieren und den Rest aus dem aktuellen Quellcode neu zu erzeugen.

Migriert CodeDoc AI Wiki-Inhalte?

Nein. CodeDoc AI liest Quellcode aus einem Git-Repository und erzeugt daraus Dokumentation — bestehende Wiki-Seiten liest es nicht. Nutze pandoc + Confluence-REST-API für eine echte Inhaltsmigration. Nutze CodeDoc AI, um die Wiki-Teilmenge „Was macht dieser Code?“ durch stets aktuelle, aus dem Quellcode erzeugte Seiten zu ersetzen.

Kann sich die Dokumentation in Confluence bei Codeänderungen automatisch aktualisieren?

Ja, wenn du den Weg der Neuerzeugung nutzt. CodeDoc AI unterstützt Webhooks (Neuerzeugung bei jedem Push oder Merge auf einen gewählten Branch) und Zeitpläne (täglich, wöchentlich, monatlich). Mit pandoc manuell migrierte Seiten aktualisieren sich nicht automatisch — sie sind statische Kopien.
